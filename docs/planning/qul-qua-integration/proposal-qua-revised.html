QUA ↔ QUL Audio Segmentation Integration

Webhook-driven, asynchronous generation of ayah / word / letter timing segments in Quranic Universal Audio (QUA), delivered to and imported by the Quranic Universal Library (QUL) — over one shared segment schema.

0QUA context & shared understanding added by QUA

Facts about how QUA produces and publishes timing data that the rest of this document builds on. These shape several of the per-section changes below.

  • Reviewed, then released on a cadence. Every recitation's segmentation passes a validation and correction cycle before its timestamps are published. Published data ships as versioned GitHub releases, cut on a cadence and batched: a fix never ships alone — it rides the next release together with every other improvement (requested corrections, model upgrades, re-runs). Confirmations therefore name a release version rather than delivering a payload.
  • Timings refer to the original source audio. QUA internally processes audio (re-encoding, trimming, one file per surah), but the published timings are keyed to the original source files — the URLs listed in the release catalog.json (audio.chapter_urls), with audio.chapter_offsets_ms where one source file serves several chapters. A different encode of "the same" recitation invalidates the timings: pair the listed URLs, or verify byte-identity. How consumer audio should be indexed long-term (original provenance vs. a mirrored canonical encode) is an open question (§13); a separate, detailed audio-integration plan will follow.
  • Timestamps are release-pinned, not stable across versions. Regeneration between releases shifts timings. The release-level manifest.json carries a per-recitation sha256 / content_hash / change_kind, and the check_updates.py helper diffs them — that is the update-detection loop.
  • Coverage semantics. A verse missing any expected word is excluded from the published data entirely — never shipped misaligned. Gaps are published per recitation as coverage.missing_surahs / coverage.missing_verses in catalog.json, so the data and the reported gaps cannot disagree.
  • Non-Quranic audio is outside the timed spans. Isti'adha, basmala, and other framing audio are excluded from the timings (they remain present in the source audio outside the timed spans). One exception: the basmala of Al-Fatiha is ayah 1:1 in Hafs — it is kept when the reciter himself sounds it, and reported as a missing ayah when it is absent or sounded by a different voice than the reciter (a spliced-in basmala is excluded like any other framing audio).
  • Word indexing. Word numbers are 1-based positions under the QPC Hafs word segmentation. A QUL mushaf_id whose word segmentation differs must be mapped on the QUL side.

1Overview & goals

QUL owns the canonical audio files and their metadata (reciters, surahs, mushaf/word references). QUA is the segmentation engine that turns an audio file into precise timing data. This integration lets QUL request segmentation on demand and receive results asynchronously, without either side blocking on long-running alignment jobs.

  • On demand. Whenever QUL needs to generate or re-generate segments for an audio file, it calls QUA.
  • Asynchronous. Segmentation can take minutes; QUA acknowledges immediately and does the work in the background.
  • Webhook callback. When segments are ready, QUA notifies QUL; QUL then pulls the results and imports them.
  • One schema. Both systems speak the same segment JSON — ayah, word, and letter timing, with first-class support for repetitions and silence.
Why pull-after-notify (not push-in-callback)? The callback stays small and cheap to retry, QUL controls when it ingests, and a large segment payload never has to survive webhook retry/size limits. This follows the well-established store-raw / respond-200 / process-async webhook pattern.

Shared identifiers

QUA and QUL must refer to the same entities by the same identifiers. Three ids are canonical across both systems and are round-tripped unchanged through every request, callback, and payload:

IdentifierTypeMeaning
audio_file_idintThe specific audio file being segmented. Same value in QUA and QUL.
reciter_idintThe reciter. Both systems share one reciter registry / id space.
surahintSurah number 1–114 (universal — no mapping needed).
Contract: neither side invents or re-maps these ids. If QUA ever needs an id QUL does not yet share (e.g. a new reciter), that reciter must be registered in the shared id space before a job references it. Ayahs and words are identified positionally ("surah:ayah" and 1-based number), which are universal.
QUA proposed changes
  • Delivery moves to GitHub releases. The notify → fetch → import legs (steps 3–5) are replaced by QUA's published, versioned GitHub releases as the single delivery surface. One artifact carries every improvement vector — requested fixes, model upgrades, re-runs — with version pinning, integrity hashes, and documented update steps; a per-job payload would fork a second contract for the same data.
  • Issue direction is reversed. QUA sends QUL audio issues (QUL owns audio and fixes it); QUL sends QUA resegmentation requests once audio is fixed or replaced. End-user reports arrive through QUA's public web UI rather than an API.
  • Shared identifiers are QUA's slugs, not a shared integer registry (see revised table below). audio_file_id stays QUL-internal and is echoed opaquely for correlation. Terminology: the qiraah field should be named riwayah — hafs, warsh, qalun, duri name riwayat (transmissions), not qiraat.

QUA proposed changes

The three legs become: a request (QUL→QUA), confirmations (QUA→QUL), and a release fetch (QUL→GitHub). A fourth, independent leg pushes audio issues QUA→QUL at any time. request_id still threads through everything.

  (1) QUL fixes/replaces audio  --- POST resegment request --->  QUA
  (2) QUA re-segments                <-- callback: accepted
                                     <-- callback: fixed { target_release }
  (3) QUA cuts GitHub release vX.Y.Z (batched, on cadence)
                                     <-- callback: released { version, release_url }
  (4) QUL fetches release assets (manifest-driven diff) and imports
  (*) QUA --- issue webhook (audio-domain issues) ---> QUL, any time

Release assets per version: one <recitation>.zip per recitation (the timing tiers, §6), a release-level manifest.json (per-recitation sha256 / content_hash / change_kind), catalog.json (recitation metadata + source audio URLs), CHANGELOG.md, static references (mushaf text, surah info, letter vocabulary CSV), and consumer helper scripts including check_updates.py. Assets are public; integrity comes from the manifest hashes. License: CC-BY-4.0.

3End-to-end flow

1
QUL requests segmentation. On a user action or automated trigger (new audio file, corrected boundaries, re-segment), QUL POSTs a job to QUA with the audio file location, generation options, a callback_url, and a QUL-generated request_id.
2
QUA acknowledges. QUA validates, persists the job, and returns 202 Accepted with a job_id and status:"queued". No segmentation happens on this request.
3
QUA generates asynchronously. A background worker performs forced alignment and produces word, letter, silence and repeat data. Status moves queued → processing → completed | failed.
4
QUA notifies QUL. On completion (or failure) QUA POSTs a small callback to QUL's callback_url. QUL stores the raw payload, responds 200 immediately, and enqueues a fetch+import job.
5
QUL fetches & imports. QUL GETs the full segment payload from QUA and imports it into Audio::Segment (word & letter timing, repetition flags, silence).

The GET status endpoint (/segmentation/jobs/:job_id) is a fallback: if the webhook is missed, QUL can poll to reconcile. The webhook is the primary signal.

QUA proposed changes
1
QUL requests resegmentation. After fixing or replacing audio, QUL POSTs a resegment request with the recitation slug, surah, the replacement audio, a scope (§4), optional issue_ids it addresses, and a QUL-generated request_id.
2
QUA acknowledges with 202 + request_id echo, then processes asynchronously.
3
QUA confirms the fix (or failure). A slim callback: fixed with the target_release the correction will ship in, or failed with an error. No segment data.
4
QUA cuts the next GitHub release on its cadence, batching this fix with everything else that landed. A second callback: released with the actual version and release URL.
5
QUL updates from the release. Diff manifest.json hashes (or run check_updates.py), download only the changed recitation zips, import. The status GET remains the reconciliation fallback for missed callbacks.

4QUA API — segmentation & issues

POST/api/v1/segmentation/jobscalled by QUL

Create a segmentation job. Idempotent on request_id — repeating the same request_id returns the existing job rather than creating a duplicate. The qiraah field is required so QUA aligns against the correct reading (e.g. Ḥafṣ vs Warsh differ in word forms and letter counts).

// Request body
{
  "request_id": "qul-9f3c2a17",        // QUL-generated, unique per logical request
  "callback_url": "https://qul.example.org/api/v1/segmentation/callbacks",
  "audio_file": {
    "id": 12345,               // QUL audio file id (echoed back)
    "url": "https://cdn.qul.example.org/audio/7/002.mp3",
    "format": "mp3",
    "duration_ms": 742000
  },
  "reciter_id": 7,
  "surah": 2,
  "qiraah": "hafs",          // narration/reading: hafs | warsh | qalun | duri | ... (required)
  "ayah_range": { "from": 1, "to": 286 },  // optional; whole surah if omitted
  "mushaf_id": 1,              // which word segmentation / script QUL expects
  "options": {
    "letters": true,            // emit letter-level segments
    "silence": true,            // emit silence metadata
    "detect_repeats": true
  }
}
// 202 Accepted
{
  "job_id": "qua-job-5521",
  "request_id": "qul-9f3c2a17",
  "status": "queued",
  "created_at": "2026-08-27T10:00:00Z"
}

QUA proposed changes

Endpoint changes

  • POST /segmentation/jobs → POST /api/v1/resegment-requests. The only inbound job type: audio was fixed/replaced, re-segment it. Idempotent on request_id as proposed.
  • GET /segmentation/jobs/:job_id → GET /api/v1/resegment-requests/:id. Kept as the poll fallback. status: queued | processing | fixed | released | failed; carries target_release once fixed and version once released.
  • GET /segmentation/jobs/:job_id/segments — removed. Segment data is delivered only via GitHub releases (§2).
  • GET /audio_files/:id/issues → GET /api/v1/recitations/:slug/issues. Kept, keyed by recitation slug, with status / type / surah filters and a global variant. New issues are additionally pushed to QUL by signed webhook (§5); the GET is for reconciliation and backfill.

Resegment request

{
  "request_id": "qul-9f3c2a17",
  "recitation": "abdulbasit_abdulsamad_mujawwad_qdc",
  "surah": 2,
  "audio": { "url": "https://cdn.qul.example.org/audio/7/002.mp3",
             "checksum": "sha256:...", "duration_ms": 742000,
             "qul_audio_file_id": 12345 },
  "scope": [ { "ayah": 5 }, { "from": 12, "to": 15 } ],   // or "full"
  "issue_ids": [ "qua-issue-8801" ],                       // optional: issues this addresses
  "notes": "re-recorded 2:5; spliced 2:12-15"              // optional
}
  • scope as a list of single ayahs and/or ranges: different parts of one file can be fixed independently. A ranged scope is a declaration that audio outside the union of the listed spans is time-preserved; QUA verifies (duration delta, spot checks) and falls back to a full re-segmentation with a notice when the declaration does not hold. Only the listed spans are re-segmented, avoiding recomputation and churn in verses whose timings were already correct.
  • scope: "full" re-segments the whole file — necessary whenever a replacement shifts the timeline and invalidates existing timings; otherwise ranged scope is preferred.

Issue catalogue — audio-domain only

Issues QUA sends are limited to what QUL, as the audio owner, can act on. Segmentation-quality findings are internal to QUA and are fixed on QUA's side.

typeMeaning
missing_ayah_audioAn entire ayah is absent from the recitation. A truncated file surfaces as a missing range ending at the surah's last ayah.
missing_word_audioOne or more specific words of an ayah have no audio.
mispronunciationA word is recited incorrectly (reported by listeners or found in review).
corrupted_audioA region is corrupted / unreadable / decodes to garbage.

Removed from the draft catalogue: truncated_audio (expressed as a trailing missing range), extra_audio (non-Quranic and stray audio is excised from the timed spans — see §0 — so it never affects the data), alignment_low_confidence (internal to QUA), abnormal_silence (surfaces as corrupted/missing audio on detection). Issues may carry a free-text comment, including listener comments where a report originated from one.

Issue lifecycle

  • QUA owns status (open | resolved). QUL-side acknowledgement/dismissal is QUL's local bookkeeping.
  • Detectable types (missing_*, corrupted_audio) resolve by re-check: after replacement audio round-trips re-segmentation, an issue closes only when the condition no longer holds — regardless of what the request claimed. A whole-file replacement is therefore safe: nothing resolves on trust.
  • Listener-reported types (mispronunciation, comment-based reports) cannot be auto-verified; they resolve when a resegment request claims them via issue_ids.

6Segment schema — the shared contract

A response envelope plus an ordered timeline array. ayah is a field, not a key — so the same ayah can appear multiple times, in the exact order it is recited. Every time value is an absolute offset from the start of the audio file, in milliseconds.

{
  "schema_version": "1.0",
  "audio_file_id": 12345,
  "reciter_id": 7,
  "surah": 2,
  "qiraah": "hafs",          // echoed from the request
  "units": "ms",
  "ends_includes_silence": true,   // convention: trailing silence is inside [start, ends]
  "segments": [
    {
      "ayah": "2:1",            // "surah:ayah"
      "start": 1000,
      "ends": 6000,
      "silence": 200,         // trailing silence in ms (0 if none)
      // "repeat" is present only when this entry is a repetition
      "words": [
        {
          "number": 1,       // 1-based word position within the ayah
          "start": 1000,
          "ends": 1500,
          "silence": 0,
          "letters": [      // omitted when options.letters = false
            { "number": 1, "text": "ا",  "start": 1000, "ends": 1120 },
            { "number": 2, "text": "ل",  "start": 1120, "ends": 1200 },
            { "number": 3, "text": "لّٰ", "start": 1200, "ends": 1380 },
            { "number": 4, "text": "هِ",  "start": 1380, "ends": 1500 }
          ]
        }
      ]
    }
  ]
}
QUA proposed changes

Two structural changes: the payload is tiered (three files per recitation — verse / word / letter granularity, so a consumer downloads only the depth it needs), and rows are compact positional arrays rather than nested named objects (the named-object shape measured 2.8× larger raw and 1.19× gzipped on a full letter tier). The ordered-timeline idea is kept exactly: the file is a flat array in recitation order, and a verse recurs once per occurrence.

// verse tier - ordered playback timeline; one row per contiguous occurrence
// row: [ref, start, end, canonical, silence_after]
[ ["55:5", 42000, 45100, 1, 0],
  ["55:6", 45100, 47000, 1, 300],
  ["55:7", 47300, 49800, 1, 500],
  ["55:5", 50300, 52400, 0, 0],        // loop-back repeat
  ["55:6", 52400, 54100, 0, 2100] ]

// word tier row:   [ref, start, end, canonical, silence_after, [[widx, start, end], ...]]
// letter tier row: adds the per-letter breakdown - specification deferred, see section 10

Each tier file carries a small _meta envelope: schema_version, recitation slug, riwayah, units: "ms". Times are absolute from the start of the chapter's source audio file (apply chapter_offsets_ms from catalog.json where present, §0).

QUA proposed changes

The named-field tables above are replaced by positional row slots:

Verse-tier row

#SlotTypeDescription
0refstring"surah:ayah". Recurs once per occurrence, in recitation order.
1startint (ms)Occurrence start.
2endint (ms)Last audible sample of the occurrence (§9).

Word tier

Appends slot 5: [[widx, start, end], ...]. widx is the 1-based word position in the ayah (QPC Hafs segmentation, §0). Within one take, widx may repeat or go backward — within-take repeats are preserved verbatim (§8); consumers must not assume monotonic word numbers. A partial occurrence carries only the words it recites.

Letter tier

Deferred pending the letter tokenization and timing contract (§10). Word text is not included at any tier (§13).

8Repetitions

Repetition is intrinsic to recitation: a reciter may repeat part of an ayah, repeat a whole ayah several times, or go back two or three ayahs and recite them again. Because the timeline is an ordered array keyed by nothing, every repetition is simply another entry in playback order. The repeat: true marker flags entries that are not the first pass; which pass it is (2nd, 3rd…) is derivable by counting prior entries with the same ayah.

Whole-ayah repeat (×3)

[
  { "ayah":"112:1", "start":0,    "ends":3000 },
  { "ayah":"112:1", "start":3000, "ends":6000, "repeat":true },
  { "ayah":"112:1", "start":6000, "ends":9000, "repeat":true }
]

First pass has no repeat. Passes 2 and 3 are marked.

Partial-ayah repeat

// full ayah, then only words 3–4 repeated
[
  { "ayah":"2:255", "start":0, "ends":8000,
    "words":[ /* 1..N */ ] },
  { "ayah":"2:255", "start":8000, "ends":9500, "repeat":true,
    "words":[
      { "number":3, "start":8000, "ends":8700 },
      { "number":4, "start":8700, "ends":9500 }
    ] }
]

Only the repeated words appear; number preserves their position in the ayah.

Loop-back over several ayahs (recite 5–7, then 5–7 again)

[
  { "ayah":"55:5" }, { "ayah":"55:6" }, { "ayah":"55:7" },
  { "ayah":"55:5", "repeat":true }, { "ayah":"55:6", "repeat":true }, { "ayah":"55:7", "repeat":true }
]

(start/ends omitted here for brevity — they are required in real payloads.) The timeline order is the recitation order; no separate grouping structure is needed.

QUA proposed changes

The ordered timeline with every repetition as its own entry is agreed — three refinements:

  • repeat: true becomes the canonical flag (slot 3), anchored to the earliest complete, continuous take rather than to "the first pass". A leading partial (the reciter starts a verse, breaks off, and restarts) can precede the complete take — "first entry unmarked" would mislabel it. Exactly one occurrence per verse is canonical; everything else is a repetition by definition, so no separate repeat marker is needed.
  • One row = one contiguous recited span. A leading or trailing partial is its own row (carrying only its recited words), never folded into the complete take — folding would poison the canonical span with non-continuous audio. Whether a repetition is full or partial is derivable from its word coverage; no kind enum.
  • Within-verse repeats inside one continuous take are not split out and not flagged. They are the natural fabric of the take (word numbers repeat or step backward mid-row, §7); filtering them would cut audio inside a continuous span. The canonical take is always continuous audio, repeats included.

9Silence

Reciters pause after words and ayahs. Each word and ayah carries a silence value: the number of milliseconds of trailing silence, 0 when there is none.

ConventionMeaning
ends_includes_silence: true recommendedThe silence is inside [start, ends]. Audible speech ends at ends − silence; the gap up to ends is the pause. Adjacent segments stay contiguous (ends of one = start of the next).
ends_includes_silence: falseends marks the last audible sample; the pause occupies the gap between this ends and the next start. silence then equals that gap and is purely informational.
Open decision (per team): we lean toward ends_includes_silence: true so segment spans are gap-free and a highlighter can hold the current word/ayah highlighted through the pause. The flag is written into every payload so consumers never have to guess. Final ratification pending. QUL already normalizes inter-ayah gaps to ~200 ms today, which this formalizes.
QUA proposed changes

Resolved — the convention is fixed, so the per-payload flag disappears:

  • end = last audible sample, always. end - start is audible duration; pauses live in the gaps between rows. (In the draft's terms: ends_includes_silence: false, permanently — no flag, no dual code paths.)
  • silence_after (verse-tier slot 4) precomputes the trailing gap for consumers whose storage is row-per-ayah. It equals next.start - end over the full timeline; a consumer that filters rows recomputes from its kept set.
  • Word-level pauses are derivable in place (next word's start minus this word's end, within the same row) — no per-word field.
  • The highlight-hold behavior that motivated the inclusive convention is one line client-side: hold the highlight until the next row's start. Consumers that surface silence instead do the opposite — de-highlight during the gap and re-highlight as recitation continues. Honest gaps also enable finer-grained consumers: e.g. playing a specific part of a verse delimited by where the reciter made waqf.

10Letters & tashkeel

Letter segments enable per-letter highlighting. A "letter" is one displayed grapheme: the base Arabic letter together with any tashkeel (harakah, shadda, madda, sukun) that sits on it. Tashkeel is never a separate letter entry.

The word اللّٰهِ segments into 4 letters:

numbertextnote
1اalif
2لlam
3لّٰlam + shadda + dagger alif — one grapheme
4هِha + kasra
  • Grouping rule: combining marks attach to the preceding base letter; the text field holds the full grapheme cluster.
  • Coverage: letters within a word are contiguous and cover the word's audible span; the sum of letter spans reconstructs the word timing.
  • Optional: the entire letters array is omitted when the job's options.letters is false.
QUA proposed changes

Deferred — the letter tier ships after a tokenization addendum. The per-letter tokenization and timing contract is under final review on QUA's side: the granularity convention (script-letter rows vs. mark-level cells), treatment of superscript/combining marks and silent carrier letters, and revisions of the source script. The draft's grouping (e.g. folding a superscript alef into its host letter as one grapheme) conflicts with QUA's current convention, where a sounding superscript alef is its own timed token — exactly the kind of decision the addendum will fix.

Pinned already, independent of the addendum:

  • Script: the letter tier is defined against the QPC Hafs Uthmani script only. Other scripts (e.g. Indopak) have different letter inventories and conventions; mapping to them is a consumer-side concern.
  • Published alphabet: the exact token set ships as a versioned CSV asset in every release (letter_vocab_<riwayah>_<script>.csv: char, codepoint, name) — a new riwayah or script adds its own file. Consumers validate tokens against it.
  • Harakat are not separate timed entries (they ride their base letter temporally); the letter rows are a timing index — display text comes from the mushaf script, matched positionally.

11Security & reliability

Authentication & integrity

  • HMAC signatures on every webhook and job request: X-QUA-Signature / X-QUL-Signature = HMAC-SHA256(body, shared_secret).
  • Timestamp header (X-Timestamp) signed alongside the body to prevent replay; reject skew > 5 min.
  • Bearer/API-key on the fetch endpoints in addition to the signature.

Idempotency & retries

  • request_id makes job creation idempotent; re-posting returns the same job.
  • Callbacks are at-least-once: QUL de-dupes on (job_id, status) and imports idempotently per audio_file_id.
  • QUA retries the callback with exponential backoff until QUL returns 2xx; QUL's GET status is the reconciliation fallback.
Receiver contract. QUL's callback endpoint must store the raw payload, respond 200 quickly (well under QUA's timeout), and do fetching/importing in a background job — never inline. This keeps the webhook resilient to slow imports.
QUA proposed changes

Adopted as proposed (HMAC-signed requests and callbacks, signed timestamp with 5-minute skew, request_id idempotency, at-least-once callbacks with backoff). Two adjustments:

  • The issue webhook (§5) is signed with the same scheme (X-QUA-Signature + X-Timestamp); QUL de-dupes/upserts on issue id.
  • No fetch-endpoint auth is needed for segment data — release assets are public; integrity comes from the manifest.json hashes, not transport auth.

12Mapping to QUL storage

The schema maps cleanly onto QUL's existing Audio::Segment model — this is a self-describing superset of what QUL already exports, so import is largely a transform, not a migration.

QUA proposed changes
  • Import source is the GitHub release, not a per-job payload: diff manifest.json hashes, download changed recitation zips, import the tier files. The import remains a transform.
  • ends vs end is moot — rows are positional; slot semantics are defined in §7.
  • has_repetition / repeated_segments derive by counting non-canonical rows per ayah; the clean single-take import is rows.filter(r => r[3] === 1).
  • Trailing-gap normalization maps from silence_after (or is recomputed after filtering, §9).
  • letter_segments import waits for the letter-tier addendum (§10).

13Open questions

  • Silence & ends: ratify ends_includes_silence: true (recommended) vs. exclusive. Written into every payload either way.
  • Field name ends vs end: keep ends in the contract (current choice) or align to QUL's export end.
  • Word text: include the word glyph in the payload for validation, or rely on number + QUL corpus only? (Currently letters carry text; words do not.)
  • Delivery of the fetch payload: inline JSON from GET …/segments vs. a pre-signed object-storage URL for very large surahs.
  • Partial re-segmentation: should ayah_range jobs patch existing segments or always replace the whole file's set?
  • Issue lifecycle: are issues resolved on QUA (re-run segmentation clears them) or acknowledged/dismissed by QUL? Define who owns status transitions.
QUA proposed changes

Resolutions proposed above:

  • Silence & ends: resolved (§9) — end = last audible sample, explicit silence_after on verse rows, no per-payload flag.
  • ends vs end: moot — positional rows (§7).
  • Word text: not included — keeps the word tier compact; the mushaf text is a shared static reference and widx is the join key.
  • Delivery: GitHub releases (§2); the pre-signed-URL question disappears with the fetch endpoint.
  • Partial re-segmentation: resolved by the scope contract (§4) — ranged scopes patch under a verified time-preservation declaration; "full" replaces.
  • Issue lifecycle: QUA owns status; detectable issues resolve by re-check after re-segmentation, listener-reported ones via issue_ids claims (§4).

Remaining open:

  • Audio indexing for consumers: original source URLs as today, or a mirrored canonical encode — a separate, detailed audio-integration plan follows (§0).
  • Letter tier: tokenization + timing contract addendum (§10).
  • Release cadence / turnaround expectations for confirmed fixes — to be agreed once request volume is known.

14Migration plan added by QUA

Staged adoption in three cohorts, split by where a recitation's audio lives today. Each phase gates the next; the existing QUL segment data stays untouched until full integration is signed off.

1
Shared recitations already on the Tarteel / QUL CDN. QUA already publishes timings keyed to these exact audio files, so there is no audio question — migrate these first. Import the new-format tiers, test and refine the importer against them, then pilot with a small group of consumers before scaling further. Recommended: surface the new data as a separate page or filter alongside the existing QUL segments, keeping the current-format segments in place until full integration; consumers opt in during the pilot rather than being switched.
2
QUA recitations not yet on QUL (audio not Tarteel-hosted). Bringing these into QUL is blocked on the audio-indexing decision (§13): whether consumers point at the original CDN provenance, the original YouTube-sourced files, a mirrored canonical encode, or Tarteel hosting. Resolved by the separate audio-integration plan; these recitations migrate once it lands.
3
QUL-only recitations into QUA. These enter QUA's processing and review pipeline before their timings publish — capacity-bound, cadence to be agreed. This phase also includes an overlap assessment: where a recitation already exists on both sides but with different audio files / links / source provenance, decide per case whether QUA realigns against QUL's audio, or QUL adopts QUA's existing audio and replaces its timings with the published ones. Conditional — applies only where such overlap is actually found.
